# 充电阈值被改回 100% —— 排查结论

> 排查日期：2026-10-22
> 现象：程序把充电阈值设为 65%/90%，一两秒后阈值变回 0%/100%（即"充到 100%"）。

## 一句话结论

**不是某个应用在抢占，是固件把 `0x1003` 的写入丢弃并回滚了。**
程序原先用 `0x1003`（SetBatteryChargeThreshlod）写阈值；固件处于「智能充电模式」时，
这条写入路径不生效，固件会在 0.2~1.3 秒内把阈值回滚到当前模式的预设值。
改用 `0x1503`（SetSmartChargeMode）写阈值后，一切正常。

## 证据链

### 1. ETW 抓包：回滚时刻没有任何 WMI 写入

用 `Microsoft-Windows-WMI-Activity` 提供程序抓 `OemWMIfun` 的 `ExecMethod` 调用：

- 整个抓包窗口内，调用 `OemWMIfun` 的客户端只有一个：`NT AUTHORITY\SYSTEM` / PID 1684
  （= `C:\Program Files\Huawei\Hiview\HiviewService.exe`）
- 它每 10 秒调 4 次，但**调用时间与阈值回滚时刻对不上**（差着几秒到十几秒）
- 把阈值改回的那一秒前后 ±2 秒窗口内，**一个 WMI 写入事件都没有**

也就是说：回滚发生时，没有任何应用在发 WMI 写命令。

### 2. 排除法：干掉华为组件，回滚照旧

| 步骤 | 结果 |
|---|---|
| 正常状态写 65/90 | 1.24 秒后回滚为 40/70 |
| `net stop "Huawei PCManager Windows Service"` 后写 | 1.11 秒后回滚为 40/70 |
| 再杀掉 `HiviewService.exe` 进程后写 | 0.32 秒后回滚为 40/70 |

服务停了、进程杀了，回滚照旧发生 —— 排除"HiviewService 抢占"这一假设。

### 3. 回滚目标 = 当前智能充电模式的预设值

用 `0x1603` 读当前模式与容量对，用 `0x1103` 读固件实际生效的阈值：

| 当前模式 | 写入 | 固件实际生效 | 回滚目标 |
|---|---|---|---|
| mode 1 (65/70) | 33/44 | → **0/100** | mode 预设 |
| mode 2 (85/90) | 33/44 | → **0/100** | mode 预设 |
| mode 3 (95/100) | 33/44 | → **0/100** | mode 预设 |
| mode 4 (自定义 20/30) | 33/44 | → **40/70** | mode 预设 |

写 `0x1003` 还会把模式本身重置成 mode 4（`0x1603` 读出的 mode 变成 4）。

### 4. 换 `0x1503` 写，阈值稳定

`0x1503` 载荷布局（来自 `WmiUtil.dll!SetSmartChargeMode` 反汇编）：

```
[0..1] = 0x1503 (LE)
[2]    = 模式号
[3]    = 0        ← 置 0 表示"用我传入的起止值"；置非 0 则走固件预设表
[4]    = 起始 %
[5]    = 结束 %
```

逐组合验证（写入后等 2 秒读一次、再等 4 秒读一次，两次都必须等于请求值）：

```
mode1   0/100 -> (0, 100)  OK      mode1  60/80  -> (60, 80)  OK
mode1   0/80  -> (0, 80)   OK      mode1  65/90  -> (65, 90)  OK
mode1   0/90  -> (0, 90)   OK      mode1  70/90  -> (70, 90)  OK
mode1  30/50  -> (30, 50)  OK      mode1  80/90  -> (80, 90)  OK
mode1  50/60  -> (50, 60)  OK      mode1  85/90  -> (85, 90)  OK
mode1  50/80  -> (50, 80)  OK      mode1  90/95  -> (90, 95)  OK
                                   mode1  90/100 -> (90,100)  OK
                                   mode1  95/100 -> (95,100)  OK
```

全部 OK，无一例外。

### 5. 固件模式号的可用性

固件有 6 个智能充电模式，用自定义阈值逐个试：

| 模式 | 请求 65/90 | 实际生效 | 可用? |
|---|---|---|---|
| 1 | 65/90 | 65/90 | ✅ |
| 2 | 65/90 | 65/90 | ✅ |
| 3 | 65/90 | 65/90 | ✅ |
| 4 | 65/90 | **40/70** | ❌ 固件固定档，忽略传入值 |
| 5 | 65/90 | 65/90 | ✅ |
| 6 | 65/90 | 65/90 | ✅ |

mode 4 请求什么都固定成 40/70，不能用。程序选用 **mode 1**。

## 修复

`src/hwbattery.c` 的 `hwmi_set_threshold()`：

- 写入路径从 `0x1003` 换成 `0x1503`（`CMD_SET_SMART_MODE` + `SMART_MODE_CUSTOM 1`）
- 写完回读一次 `0x1103` 校验实际生效值，不再只看"返回 0 即成功"

C 侧构造的 8 字节载荷与已验证的 Python 实现逐字节一致：

```
65/90   cmd=0x5A4100011503  bytes=03 15 01 00 41 5A 00 00
0/100   cmd=0x640000011503  bytes=03 15 01 00 00 64 00 00
40/70   cmd=0x462800011503  bytes=03 15 01 00 28 46 00 00
95/100  cmd=0x645F00011503  bytes=03 15 01 00 5F 64 00 00
```

端到端验证：新编译的 exe 启动下发 40/80，日志记录「启动下发配置成功：起始 40% 截止 80%」，
随后 30 秒内多次回读均为 40/80，不再回滚。

## 顺带记下的两条读取路径

两条路径返回布局完全不同，**不可混用**：

| 命令字 | 语义 | 布局 |
|---|---|---|
| `0x1103` | 读固件实际生效的阈值 | 自末尾向前找最后一个非零字节 `out[i]`（`i >= 2`），则 `start = out[i-1]`、`end = out[i]` |
| `0x1603` | 读智能充电模式与容量对 | 固定偏移：`out[1]` = 模式（须 < 7），`out[3]` / `out[4]` = 容量对 |

`0x1103` 不在任何华为 DLL 里（`WmiUtil.dll` / `SmartChargePlugin.dll` 全文件穷举 `03 11` 零命中，
唯一命中是 `call qword ptr [rip+...]` 的跳转位移），它由固件响应，
与 Linux 主线驱动 `drivers/platform/x86/huawei-wmi.c` 的 `BATTERY_THRESH_GET` 同源。

## 排查用过的手段（供复现）

- **ETW**：`logman start X -p "Microsoft-Windows-WMI-Activity" 0x8000000000000000 0x05 -ets -o out.etl`，
  再 `tracerpt out.etl -o out.csv -of CSV -y`。事件 ID 11 记录 `ExecMethod` 的调用方 PID。
  注意 `Clock-Time` 是 FILETIME，换算 `unix = (t/10 - 11644473600000000) / 1e6`。
- **双视图对照**：同一时刻读 `0x1103` 与 `0x1603`，能看出"固件实际生效值"和"模式预设值"的差异。
- **高频轮询**：另起进程用持久 WMI 连接每 50 ms 读一次，才能把回滚延迟测准到 0.2~1.3 秒。

- 进程 `HiviewService.exe`：实验中杀掉过，服务已把它拉起（当前 PID 与原 PID 不同）
